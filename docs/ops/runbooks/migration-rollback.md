# Runbook — migration の切り戻し

**Status:** Draft
**Last Updated:** 2026-09-19
**リハーサル:** 未実施

## 前提: down migration は存在しない

`supabase/migrations/` にあるのは適用順の forward migration のみである。down スクリプト
は書かれておらず、CLI に「一つ戻す」操作は無い。

**切り戻しとは、逆向きの migration を新しく書いて適用することである。** これが本
runbook の全体を規定する。適用済みの migration ファイルを編集してはならない。編集して
も本番には反映されず、ローカルの `pnpm db:reset` と本番の実態が食い違うだけになる。

## 判断: 戻せるものと戻せないもの

| 直前の変更 | 切り戻し |
| --- | --- |
| テーブル・列の追加 | 可。drop する migration を書く |
| index・constraint の追加 | 可。drop する migration を書く |
| policy / function の変更 | 可。旧定義で `create or replace` する migration を書く |
| 列・テーブルの削除 | **不可。データが消えている**。下記「データが失われた場合」へ |
| 型の縮小・値の変換 | **原則不可**。元の値は復元できない |

判断の分岐点は「データが消えたか」だけである。スキーマの形は書き戻せるが、中身は
書き戻せない。

## 手順（データが失われていない場合）

1. **止める。** 追加の migration を適用しない。原因の migration を特定する。
2. **逆向きの migration を書く。** ファイル名は現在時刻で新規に採番する。中身は直前の
   migration が行ったことの逆。
3. **ローカルで確かめる。** `pnpm db:verify` を通す。これは `db:reset` →
   `db:types:check` → `db:test` の順で、**適用順の全 migration を空の DB に流し直す**。
   途中の migration が壊れていればここで落ちる。
4. **型ドリフトを解消する。** スキーマを変えた migration は `src/lib/database.types.ts`
   を古くする。`pnpm db:types` で再生成し、同じ PR に含める。
   `src/lib/database.types.ts` が単一の出所である（DH-18）。
5. **本番に適用する。** 適用後、`pnpm db:types:check` が CI で緑であることを確認する。

## 手順（データが失われた場合）

コードでは戻せない。Supabase 側の復旧に切り替える。

1. **書き込みを止める。** 復旧点より後の書き込みは、復元時に失われる。
2. **Supabase プロジェクトのバックアップ / Point-in-Time Recovery から復元する。**
   *未検証* — 対象プロジェクトで PITR が有効かどうかは未確認である。**本番稼働前に、
   PITR の有効化と保持期間を確認し、ここに記録すること。** 無効であれば、日次バックアップ
   の粒度までしか戻せない。
3. **復元点から現在までの差分を把握する。** 復元は、その間に承認された Revision と
   登録された Organization を巻き戻す。審査結果が消えるため、
   `event_revision_audit_log` を復元前後で突き合わせ、消えた承認を主催者に通知する。
4. **R2 は復元されない。** ストレージは別系統である。
   [media-recovery.md](media-recovery.md) の不整合の節を参照。

## 破壊的変更を安全に出す（事前の手順）

上の「不可」を避けるのは、切り戻しではなく出し方である。列の削除・NOT NULL 化・型の
変更は、**二つの migration に分けて別々にデプロイする。**

1. 一つ目: 追加のみ。新しい列を nullable で足し、コードが両方を読めるようにする。
2. デプロイして安定を確認する。
3. 二つ目: 削除。旧列を落とす。この時点で、旧コードへの切り戻しは不可能になる。

二つ目を出すまでは、Worker をいつでも切り戻せる。
[deployment.md](deployment.md) の「前方互換」はこの区別を指している。

## やってはいけないこと

- **`pnpm db:reset` を本番に向けない。** スクリプトは `--local` 固定であり本番には届か
  ないが、同等の操作を手で組み立てないこと。DB を作り直す操作であり、復元ではない。
- **適用済み migration ファイルの編集。** 本番には反映されず、ローカルとの乖離だけを生む。
- **型再生成の省略。** `db:types:check` は CI で落ちる。落ちたときに型ファイルを手で
  書き換えて通さないこと。migration とスキーマの乖離を隠すことになる。

## 未解決

- migration の適用記録（いつ誰が本番に push したか）が残らない。deploy workflow が
  無いことの帰結である。
