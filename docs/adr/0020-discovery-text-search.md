# ADR-0020: 探索のテキスト検索を射影上で行う

**Status:** Accepted
**Proposed:** 2026-09-20
**Accepted:** 2026-09-23

## Context

REQ-DISCOVERY-003 は「Event 名、Artist 名、Venue 名、Organization 名を検索できること」を
求めている。実装方法は決まっていない。

前提として、`src/features/discovery/queries.ts` の `loadPublicEvents` は公開中の Event を
すべて読み込み、`matchesFilters` がアプリケーション層で地域・日付・Event Type を絞る。
RLS が可視範囲を決めているため、この読み込み自体が「Visitor が読めるもの全部」である。
絞り込みが一箇所にまとまっていることが、地域と日付を同一 Schedule が満たすという
REQ-DISCOVERY-002 の規則を単体テストできる理由になっている。

日本語には語境界が無い。PostgreSQL の標準全文検索は空白区切りを前提とするため、
「コンテンポラリー」で「コンテンポラリーダンス」を引けない。実用的な全文検索には
pg_bigm または pgroonga が必要だが、Supabase の managed Postgres はどちらも提供して
いない。したがって選択肢は実質的に、SQL 側の部分一致か、アプリケーション層の照合かに
なる。pg_trgm は CJK に対して有効なトライグラムをほとんど作れず、この用途では使えない。

## Decision

テキスト検索を、既に読み込まれている射影の上でアプリケーション層の照合として実装する。
SQL に検索条件を持たせず、インデックスも追加しない。

1. 照合対象は Event 名、説明、Artist 名、Venue 名、Organization 名とする。Artist 名は
   この決定のために射影へ追加する。
2. 照合は部分一致とする。日本語に語境界が無いため、これが期待される意味である。
3. 比較前に NFKC 正規化と小文字化を行う。全角・半角の違いと英字の大小で取りこぼさない
   ようにするため。
4. 空白で区切られた複数語は AND とする。すべての語がいずれかの対象に含まれれば一致と
   する。語ごとに別の対象に当たってもよい（「山田 渋谷」で Artist 名と Venue 名に
   またがって一致する）。
5. 検索は既存の絞り込みと同じ経路に置き、`matchesFilters` の一部とする。検索と地域・
   日付・Event Type は合成される。

## Alternatives considered

### SQL の ILIKE

`event_revisions.title ilike '%語%'` で絞る。データ量が増えても転送量が増えない。

採用しない。対象が 4 つのテーブルに分かれており、`events` と `event_revisions` が相互
参照するため埋め込み join が曖昧になる。OR 条件を張るには読み込みを組み替える必要が
あり、絞り込みが SQL とアプリケーション層の二箇所に分かれる。REQ-DISCOVERY-002 の
規則が単体テストできなくなる代償が、現在のデータ量に対して見合わない。先頭一致でない
限りインデックスも効かないため、性能上の利点も現時点では理論上のものにとどまる。

### pg_bigm / pgroonga による全文検索

日本語として正しい全文検索になる。表記ゆれと語形の吸収もできる。

採用しない。Supabase の managed Postgres で利用できない。自前で Postgres を運用する
判断が先に必要であり、ADR-0002 を覆すことになる。

### 外部検索サービス（Algolia、Meilisearch 等）

品質と応答速度は最も良い。

採用しない。MVP の規模に対して運用対象と費用が増えすぎる。インデックスの同期という
新しい整合性の問題も持ち込む。

## Consequences

- 検索のために migration も生成型の変更も発生しない。
- 検索・地域・日付・Event Type がひとつの述語に集まり、同じ単体テストで検証できる。
- **1 リクエストあたり公開 Event を全件読み込む。** これは検索が持ち込んだ性質ではなく
  既存の実装の性質だが、検索を追加することでこの構造への依存が強まる。数百件では
  問題にならず、数万件では誤りである。
- 検索結果の関連度順は無い。既存の探索順（開催予定が先、終了・中止が後）のままになる。
- 表記ゆれ（「ヤマダ」と「山田」、「Ｙａｍａｄａ」と「Yamada」）は NFKC が吸収する範囲
  までしか一致しない。読み仮名による検索はできない。

## Revisit when

- 公開 Event が数千件に達したとき。全件読み込みの前提が崩れる時期であり、検索だけで
  なく `loadPublicEvents` 全体を設計し直す契機になる。
- 検索の取りこぼしが利用者から報告されたとき。表記ゆれと読み仮名の要求が実際に出て
  いるかを見て、全文検索基盤の導入を判断する。
- Supabase が日本語全文検索の拡張を提供したとき。
