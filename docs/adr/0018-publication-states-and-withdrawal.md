# ADR-0018: 公開状態と取り下げ

**Status:** Accepted
**Accepted:** 2026-09-19

## Context

`docs/plans/mvp-implementation-roadmap.md` の MVP outcome は「公開後の変更と中止も審査対象とし、過去・中止 Event を削除しない」と定めていた。上演の記録を残すことをサービスの価値の一つと位置づけていたためである。

しかし、立ち上げ期の運用を検討した結果、この方針は以下と衝突する。

- 代理入力によって掲載在庫を確保する方針を採る場合、主催者は自らの意思で掲載を始めていない。その状態で取り下げに応じられないことは、主催者との関係において成立しない。
- 「掲載したら消せない」という条件は、営業段階での摩擦として大きい。掲載在庫の確保が最優先である現段階では、この摩擦のコストが記録を残す価値を上回る。
- 出演者の氏名が半永久的に残ることは、シーンを離れた者、改名した者、特定の共演関係を残したくない者にとって不利益になり得る。

一方、以下は失いたくない。

- ADR-0007 が定める Event Revision の承認履歴と公開 Revision。
- 将来の統計・年鑑のための集計母数。
- 中止になった公演の情報。チケット購入者にとって中止の事実は実害のある情報であり、主催者の都合で消えることは観客に対する不利益になる。

## Decision

Event の公開状態を三つに定義する。

| 状態 | 発動条件 | 一覧・検索 | 直 URL | レコード |
| --- | --- | --- | --- | --- |
| `published` | 承認済み | 表示 | 表示 | 保持 |
| `cancelled` | 中止・延期の申告 | 中止として表示 | 表示 | 保持 |
| `withdrawn` | 取り下げ要請等 | 非表示 | 非表示 | 保持 |

1. 主催者からの取り下げ要請には、理由を問わず応じる。公開後であっても応じる。
2. 取り下げは物理削除ではなく `withdrawn` 状態への遷移として実装する。一覧・検索・直 URL のいずれからも到達できない。外部から見た挙動は削除と同等である。内部的にはレコードを保持し、承認履歴・公開 Revision・集計母数を失わない。
3. 利用規約および主催者への通知における表現は「削除」とする。`withdrawn` は内部の実装語であり、利用者に対して説明の複雑さを持ち込まない。
4. 中止と取り下げは別の状態として扱う。中止は `cancelled` として表示を維持する。主催者が中止情報そのものの掲載を望まない場合は、取り下げ要請として処理する。
5. 出演者本人からの氏名・画像の削除要請は、Event 全体を `withdrawn` にせず、当該箇所の部分削除として処理する。

条文としての運用規則は `docs/product/listing-policy.md` F に置く。

## Alternatives considered

### 従来方針の維持（削除しない）

「上演は消える。記録は残す」というポジショニングを保持でき、既存の情報チャネルに対する明確な差別化になる。統計と年鑑の基盤も無条件に確保できる。

採用しない。代理入力による在庫確保と両立せず、立ち上げ期の営業摩擦が大きすぎる。記録の価値は、掲載在庫が積み上がった後でなければ発生しない。

### 完全な物理削除

主催者への説明が最も明快で、個人情報の取り扱いとしても安全である。

採用しない。ADR-0007 が前提とする承認履歴を失う。また、統計の集計母数に穴が開き、年鑑の信頼性が損なわれる。外部から見た挙動は `withdrawn` と同一であるため、物理削除を選ぶ利益が小さい。

### 猶予期間つきの取り下げ（公開後 N 日以内のみ可）

誤登録の救済窓口として機能し、記録を残す方針とも部分的に両立する。

採用しない。期限管理が必要になり、期限後に取り下げを求められた場合の対応が結局必要になる。猶予期間の長さに根拠がない。

### 一覧からの非公開のみ（直 URL は維持）

実装が軽い。

採用しない。主催者にも観客にも説明が難しく、消したと言えない。取り下げ要請に応じたという約束を果たしていない。

## Consequences

- `docs/plans/mvp-implementation-roadmap.md` の MVP outcome から「過去・中止 Event を削除しない」を撤回する。本 PR で同文を改訂する。
- スキーマ変更が必要。Event の公開状態に `withdrawn` を追加し、遷移日時と処理理由を保持する。migration は本 ADR とは別に行う。
- 一覧・検索・sitemap・構造化データのすべてから `withdrawn` を除外する必要がある。除外漏れは約束違反に直結するため、authorization と同様に negative test の対象とする。
- 統計の集計は `withdrawn` を含むか含まないかを明示的に決める必要がある。現時点の想定は、シーン規模の統計には含め、個別 Event として表示する箇所には含めない。
- 代理入力の前提が成立する。主催者が望めば消せるという条件のもとで、公開情報の転記を行える。
- マーケティング上、記録の永続性を訴求できない。訴求の軸は発見と編集的なトーンに置く。

## Revisit when

- 掲載在庫が十分に積み上がり、主催者が自発的に掲載するようになったとき。取り下げ要請の実績件数を見て、記録を残す方針への回帰を検討できる。
- 取り下げ要請が想定を超えて多発したとき。掲載の合意形成に問題がある兆候として扱う。
- 統計・年鑑を外部に公開するとき。`withdrawn` を集計に含める判断の妥当性を再確認する。
